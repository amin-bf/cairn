Cairn · the pass ADR-0006 §10 opened

Layout wireframes

Every screen the twenty-eight ADRs specify, arranged. No palette, no type, no spacing decisions — those are a separate pass and this artifact deliberately does not take them.

What is settled already

What every surface says, and when it appears. The ADRs did that work. Nothing here re-decides it.

What this settles

Arrangement. Where a thing sits, which affordance carries an operation, what yields when the screen shrinks.

What is still open

Finish. Colour, typography, spacing, case. Including whether the box badge reads Box 3 or box 3.

First, a word that names two jobs

Fourteen ADRs name “the visual design pass”. Reading the handoffs side by side, they are not asking for one thing. ADR-0006 §10 opened it as a look-and-feel question — “colors, typography, spacing”. ADR-0021 §10 and ADR-0018 put where a row sits and whether reordering is a drag into the same bag. Those have different dependencies: arrangement is constrained hard by the ADRs, and finish is genuinely free.

ADR-0021's own Context already draws the line without naming it — “what an entry says, where it sits and when it appears were answerable without knowing a single colour.” So the term wants splitting:

Six arrangement decisions

Each one was left open on purpose by an ADR. The alternatives are the ones those ADRs named.

D1

The nav row is pinned to the top, and yields to the soft keyboard

decided · in CONTEXT.md

This is the one decision that touches a stated constraint from both sides, so it is first. ADR-0021 §1 requires all three destinations to be reachable “from a persistent affordance”, because “a destination reachable only by completing a session is not reachable”. ADR-0025's Consequences make the form pane's first screen “a specified resource”, with the destructive-edit warning moved into it because nowhere else works. A pinned bar spends that resource; a scrolling one is not persistent.

OptionCost
Scrolls with the content what lib.rs:448 does todayHonest about the resource, but the affordance is not persistent — you can be deep in a note list with no way out on screen.
Always pinnedCosts ~48dp of the 565dp that survives a keyboard, out of the exact band the warning was moved into.
Pinned, and hidden while the soft keyboard is upFull height for typing; the bar returns the moment the keyboard goes down. One rule, one fact.

The third is only expressible because ADR-0026 §5 made the inset seam distinguish no soft keyboard on this platform from keyboard down. On desktop the seam says the first, so the bar is simply always pinned — that is one rule reading one fact, not platform-conditional behaviour, so client-stack rule 3 is untouched.

D2

Reordering is two taps, not a drag

decided

ADR-0021 §4 fixed the operation — “place this note before/after that one”, one write — and explicitly declined to pin the gesture, noting that “long-press-drag in a scrolling list is genuinely poor on a phone, so pinning the spec to a drag would decide a handset interaction from a desktop assumption.”

So: tap Move on a row, and every gap between rows becomes a target. Tap one. It is the specified operation rendered literally, it is identical under touch and mouse (ADR-0006 §5's finding, preserved), it needs no long-press and no auto-scroll, and it is well-defined inside a filtered list — you are placing between two visible neighbours, which is exactly what §4 says the order key buys.

D3

New note sits at the top of the list and the bottom of the editor

Two placements for one action, and the asymmetry is the point. Top of the note list, because ADR-0021 §4 warns that “the end of the deck I am looking at” is the intuitive misreading and is not expressible — a new note goes to the end of the collection's order. A create button at the bottom of a filtered list asserts the misreading with its position. Bottom of the editor's form pane, because under ADR-0021 §7's autosave there is no Save button competing for that spot — §10 of that ADR says as much — and it is the one control there a phone cannot reach by accelerator.

D4

The two panes split on width; the toggle carries the dormant marker

ADR-0025 §5 measured that both panes fit on the handset, so “the toggle stands on its own merits rather than on necessity”. It keeps them: the card pane's job is “what will I be asked”, which wants a card drawn at card size, not a column half a phone wide. The · 1 dormant marker rides the toggle — and is never the warning, which ADR-0018 §4 established a count cannot be.

D5

One screen draws no nav row: the import / restore preview

ADR-0022 §6: three entry points, one screen, and it must be cold-start capable because the Android launch intent “can cold-start the application directly into an import”. It is explicitly not an overlay and not the notice channel. So it cannot be drawn inside a destination — there may not be one yet. It takes the screen, and cancelling from a cold start lands on the count picker. The file list is a different thing and does live in Settings (ADR-0022 §9), because it is the only inbound surface that needs a home.

D6

The notice channel is one line beneath the nav row, on every destination

ADR-0015 §5 gives it exactly two speakers — a dead grant, and ADR-0004 §8's clock-skew warning — and requires persistent and non-modal. Below the nav row is the only place that is all three without becoming a status area: it is empty almost always, so it costs nothing when silent, and it cannot be mistaken for a sync indicator because there isn't one. No badge, no icon, no checkmark, no “syncing…”, anywhere in the chrome, ever.

This was an ADR question, not a layout one — which is why the pass could not take it alone. ADR-0021 §6 fixed the action “at any point in the card's life”, and its argument is ADR-0010 §7's: the honest diagnosis of most leeches is a defective card, and routing you there only from the end-of-session pointer means carrying “the note about X was wrong” across twenty more cards. “The moment a defective card can be diagnosed is the moment it is in front of you.”

For restricting it to post-revealFor keeping it before

It would delete a rule rather than add one. “Entering the editor counts as a reveal” exists solely for the pre-reveal case — after reveal the card is already revealed and the clause has nothing to do. Restrict Edit to post-reveal and ADR-0006 §3's amendment becomes dead text.

Most defects — asks two facts at once, ambiguous answer, typo in the back — are only visible once you have seen both sides.

And it removes your original hazard outright rather than mitigating it: no pre-reveal control, no accidental reveal.

One class of defect is judgeable only before the reveal, and the loss is one-directional. “Is this prompt answerable?” — ambiguous, gives away its own answer, malformed markup — is a question you cannot ask once you know what it wanted. After reveal you are contaminated: you can no longer tell whether the prompt was findable or whether you simply now know.

That is the same shape as ADR-0006 §4's own reasoning about grading, one step earlier.

My read: the second column is the stronger argument but the rarer case, and the first column is right that the reveal-counting machinery has no other customer. Either way the change amends ADR-0021 §6 and ADR-0006 §3, so it wants an ADR — see Q5.

Resolved: restrict to post-reveal. Placement and this question turned out to be one question — the full-width button you preferred is where the accidental-reveal cost is highest, and that cost exists only pre-reveal. So you keep the layout and it stops costing anything. ADR-0029 is written, the two amended ADRs carry inline notes, review.rs implements it, and a test guards it — verified by injecting the regression and watching the test fail, since a guard that cannot fail guards nothing.
