# ADR-0017: Card slots — a card's ordinal is assigned, not positional

- **Status**: Accepted
- **Date**: 2026-07-31
- **Resolves**: [Decide: whether `CardRef` carries a kind discriminator](https://github.com/amin-bf/cairn/issues/55)

## Context

[ADR-0012 §6](0012-the-note-authoring-experience.md) recorded the sharpest finding of the authoring
prototype and could not fix it. A card is `CardRef { note, ordinal }`
([ADR-0002 §6](0002-the-card-model.md)) and the ordinal is *the index into the current kind's `cards`
list*. The kind is not part of the identity. So switching a `vocab` note to `cloze` puts blank 1 at
ordinal 1 — the slot the `Meaning → Term` card held — and ADR-0002 §7's replay rule projects that
card's reviews onto a blank the user has never seen. Nothing marks it dormant, because ordinal 1 *is*
generated; it is generated by a different question. The scheduler then believes a fresh blank carries
a history and a stability it never earned.

It cannot be fixed downstream. Content edits are deliberately not log events (ADR-0002 §7), so replay
can never learn what kind a note used to be.

ADR-0012 §6 handed ADR-0002 two options: accept the hazard and warn at the kind change, or put a kind
discriminator into `CardRef`. This ADR takes neither. Both treat the ordinal's *meaning* as given and
argue about the identity's *encoding*; the defect is in the rule that **assigns** ordinals, and fixing
it there costs nothing downstream.

## Decision

### 1. A card's ordinal is a slot number declared in the kind definition

ADR-0002 §4's `cards` list stops being positional. Each entry declares an explicit **slot**, drawn
from one namespace shared by every kind in the collection:

```
basic          cards: [ {slot 0, Front→Back} ]
basic-reverse  cards: [ {slot 0, Front→Back}, {slot 1, Back→Front} ]
vocab          cards: [ {slot 2, Term→Meaning}, {slot 3, Meaning→Term} ]
cloze          blank n → slot 0x8000 | n                                   (§3)
```

`CardRef` is unchanged: `{ note: NoteId, ordinal: u16 }`, and the ordinal is the slot. ADR-0002 §6's
canonical encoding is untouched — 16 UUID bytes then the ordinal big-endian, eighteen bytes — so
ADR-0001 §7's fuzz seed, every row in the log ([ADR-0004 §5](0004-the-review-event-log.md)),
ADR-0010's suspension keys and the `.ldeck` format all move not at all. **This decision changes no
byte of any persisted artifact.** It changes which number goes in a field that already exists.

### 2. `basic` and `basic-reverse` share slot 0 deliberately, and that is the requirement that decided this

The transition table, derived from ADR-0002 §4's own definitions, is what rules out the discriminator:

| kind change | ordinal 0 | ordinal 1 | reattachment |
|---|---|---|---|
| `basic` → `basic-reverse` | Front→Back → Front→Back | — → Back→Front | **correct** |
| `vocab` → `cloze` | Term→Meaning → *(none)* | Meaning→Term → blank 1 | wrong |
| `vocab` → `basic` | Term→Meaning → Front→Back | Meaning→Term → *(none)* | wrong |
| `cloze` → `vocab` | *(none)* → Term→Meaning | blank 1 → Meaning→Term | wrong |

ADR-0012 §6 found row two. Row one is the case it did not look at, and it is **the most likely kind
change a user ever makes** — *I want the reverse direction too*. There ordinal 0 means Front→Back
under both definitions, so history reattaching is exactly right.

**A kind discriminator in `CardRef` breaks it.** Making the identity kind-scoped orphans every review
of a card that is literally the same question, under the same "projects onto nothing" rule and with
the same silence. That trades a rare wrong reattachment for a common wrong orphaning, and the
orphaning is worse: the hazard is at least visible in the editor, which knows the before and the
after, whereas history quietly failing to reattach after a `basic-reverse` switch looks like nothing
happened at all.

Explicit slots meet the requirement *by construction* rather than by luck. Two kinds share a slot
when and only when they mean the same card, and the definition says so in the one place a reader
looks.

Rejected: **a kind discriminator in `CardRef`** (ADR-0012 §6's option 2), on the above, and
independently on cost — the kind is a variable-length string (ADR-0002 §2), so admitting it makes the
18-byte encoding variable-length and reaches the fuzz seed, the log and the export.

Rejected: **accept the hazard and warn** (ADR-0012 §6's option 1). It leaves a real defect that the
warning merely narrates; a user who clicks through has silently poisoned a card's stability with no
downstream repair. And the cost comparison is not close, because of §7.

### 3. Cloze blanks are partitioned by the high bit

A cloze blank `n` occupies slot `0x8000 | n`. Fixed-arity slots occupy `0x0000–0x7FFF`.

Cloze slots are not declared in a definition at all — they are authored blank numbers, unbounded and
chosen by the user (ADR-0002 §5) — so the registry has to stay disjoint from them without ever being
able to see them. The high bit makes that disjointness a property of the type: there is nothing to
enforce and nothing to check, and the one bit *is* the check.

The cap this implies is 32,767 blanks in a single note. [ADR-0012 §3](0012-the-note-authoring-experience.md)
numbers each new blank one above the highest ever used and never reuses, so a heavily-edited note does
drift upward; reaching the cap means creating and discarding 32,767 blanks in one note, which is not a
real document.

**Accepted cost, stated because it is a real loss:** a raw log row gets harder to read by hand. ADR-0004
§5's example reads `card note abc, ordinal 0`; under this rule a cloze blank 1 writes `ordinal 32769`,
and the blank number is `ordinal & 0x7FFF`. The interchange form is JSON lines and thus semi-inspectable,
so this costs a decoding step in a diagnostic tool. Taken over the alternatives: a reserved base constant
(`1024 + n`) reads better but makes disjointness a number someone can drift past, failing silently; and
widening the ordinal to `u32` reaches the 18-byte encoding, which is the cost §1 exists to avoid.

### 4. The most destructive edit in the codebase becomes a test

ADR-0002 §4 binds anyone editing a kind definition: *"The `cards` list may only be appended to. Never
reorder, never remove"*, and calls reordering **the single most destructive edit available in this
codebase**. Explicit slots do not abolish that danger, they **relocate** it. The destructive edit is
now *changing a slot number on an existing entry, or reusing a number for a different question*.

**The old rule is replaced, not supplemented.** Keeping "never reorder" alongside explicit slots would
be false comfort and actively harmful: it teaches the next reader that position still means something,
which is exactly the doubt that produces code reading the list index instead of the slot field. One
rule, in one place:

> **A slot number is the card's identity. Never change one, never reuse one for a different question.
> List order is free.**

The reason this is a larger win than a tidier rule: **it is checkable and its predecessor was not.**
"Never reorder a list" can only be enforced by a human noticing it in a diff, which is why ADR-0002 §4
could do no more than name the danger. The new rule is two tests over the shipped definition table —
uniqueness of slot numbers, and immutability against a checked-in golden list of `slot → (prompt,
answer)`. That converts the most dangerous edit in the repository from a documented prohibition into a
red build, which matters disproportionately here: the destination fixes that **agents implement this**,
and an agent reads a failing test far more reliably than a prohibition in an ADR nobody pointed it at.

> **Widened by [ADR-0018 §3](0018-the-card-pane-ordering.md): the golden `slot → (prompt, answer)` list
> is also a *runtime* lookup**, not only a test fixture. Naming a dormant card requires it — the note's
> current kind does not declare the slot, so the pane resolves the name across every definition the
> collection holds, and that is answerable **only** because §1 makes a slot mean one question
> collection-wide. The price of a slot missing from the table rises accordingly: it broke a test, and
> now also degrades a user-visible name to ADR-0018 §3's bare-number case, which fails silently where
> the test fails loudly.

### 5. The kind change stops being a special case

[ADR-0012 §6](0012-the-note-authoring-experience.md)'s bespoke warning — *"changing kind must state
which ordinals already carry history, because that is the set at risk"* — is **retired**. With disjoint
slots there is no set at risk. A kind change can no longer retype history onto a different question;
it can only make cards **dormant**, which is ordinary behaviour the model already names and handles.

It therefore folds into [ADR-0012 §5](0012-the-note-authoring-experience.md)'s existing ambient
dormancy warning with nothing added. That warning already recomputes dormancy from the draft every
frame, holds the dormant card in ordinal position in the card pane with its history in words, and
offers Undo. `vocab` → `cloze` shows two dormant cards instead of one, and §5's copy is true unchanged:
nothing is deleted, the reviews stay in the log, and they reattach by themselves if the content
returns — switching back to `vocab` genuinely restores them.

This is the shape of the win, and it is a shape this repository keeps arriving at. ADR-0012 §6 called
the hazard *"the finding that outranks everything else here"* and could only record it. This ADR does
not handle it; it makes it **stop arising** — as ADR-0002 §7 removed card retirement and ADR-0011
removed the daily-limit questions rather than answering them.

**Handed to the visual design pass, rather than settled here:** under §3's partition, a `vocab` note
switched to `cloze` has dormant cards at slots 2 and 3 and its live blank at 32769, so ADR-0012 §5's
"in ordinal position" now sorts **both dormant cards above the live one**. For a pane whose job
[ADR-0012 §1](0012-the-note-authoring-experience.md) defines as *"what will I be asked"*, leading with
two dormant cards is arguably wrong. The ordering is a layout question, not an identity one; it is
recorded so that §5's rule does not quietly produce it unnoticed.

> **Discharged by [ADR-0018](0018-the-card-pane-ordering.md), and it was not a layout question.**
> ADR-0012 §5's rule **stands**, sorting on the raw slot number. Two corrections to the paragraph
> above: the case is not cloze's — `basic` → `vocab` leads with a dormant card with no cloze in it, the
> general shape being any change whose old slots sort below its new ones — and "leading with two
> dormant cards" assumed a full-size dormant card, which ADR-0012 §5 never specified and which the
> model usually cannot produce, a dormant card being the *absence* of a generated card. Rendered as a
> **line**, it costs two lines. The masked value `ordinal & 0x7FFF` was rejected as a sort key for
> asserting an adjacency §3 partitioned these namespaces precisely to deny — **the mask is a name,
> never a sort key**.

### 6. An imported file imposes nothing on the registry

[ADR-0008 §7](0008-the-deck-export-format.md) lets a collection hold kind definitions **acquired from
an imported file**, for kinds the running build does not ship. Those definitions carry slot numbers,
and a stranger's file may declare a kind whose slot is `0` — the number `basic` uses.

**No validation, no importer rule, no rejection.** The collision is harmless, and this is written down
because it looks unsafe and is not: a card is `(note UUID, slot)`, so two kinds sharing a slot produce
the same `CardRef` only for **the same note**. A note that arrived carrying an acquired kind and a note
of kind `basic` are different notes with different UUIDs, so a stranger's slot 0 and ours are simply
different cards. Global uniqueness is what makes *transitions* safe; it was never a property files have
to respect.

That holds only while a note cannot be switched *into* an acquired kind, so the rule that keeps it true:

> **ADR-0012 §2's kind dropdown lists the shipped kinds, plus the note's own current kind when that
> kind was acquired.**

A note of an imported kind shows its own kind, can be switched away from it, and can be switched back —
so reversibility survives, and with it §5's "they reattach by themselves". No note can adopt a slot
namespace this codebase did not mint.

The payoff: the registry stays a **codebase discipline rather than a file-format invariant**.
`leitner-export`'s importer gains no check, AGENTS.md's deck-export rules are untouched, and
ADR-0008's "a shipped definition always wins" keeps doing exactly the job it already does.

### 7. Why this is decided now and not later

Nothing is implemented and no log rows exist, so this is a text edit to a specification. After the
first review is written it is a migration on an append-only log, which ADR-0004 §10 forbids and
ADR-0007 §9 has no mechanism for — every device holds the whole log and rows are relayed byte for
byte, so no build can reinterpret another's ordinals.

This is the argument [ADR-0002 §1](0002-the-card-model.md) used to take the note layer against a
simpler flat model — *"adding the note layer later is a migration on an append-only log while the
reverse is free"* — applied to the numbering inside that layer. The asymmetry is the whole reason the
cheap option loses: accept-and-warn is cheaper today and unaffordable for the rest of the collection's
life.

### 8. `CardRef` gains no discriminator, and the question does not return

Recorded plainly, because the ticket's title asks it: **no.** The kind is not part of a card's
identity and will not become part of it. If a future kind change needs history to survive, the
mechanism already exists and is §1's — give the two kinds the same slot, deliberately, in the
definition.

## Amendments to accepted ADRs

- **ADR-0002 §4** — the `cards` list is no longer positional; each entry declares a slot, and the
  "never reorder, never remove" rule is **replaced** by §4 above's slot rule.
- **ADR-0002 §5** — its justification is corrected. It defends the cloze/fixed-arity numbering
  mismatch on the ground that *"the two never occur in the same note"*, which is **false and is the
  defect**: a note that changes kind is precisely one where both schemes occur in the same note across
  its lifetime. §5 talked itself out of the hazard one sentence before ADR-0012 found it by driving the
  editor. The clause is now true by construction rather than by assumption, via §3's partition.
  **Authored blank numbers still start at 1** — the number the user types in `{{1::…}}` is theirs, and
  ADR-0012 §3's "one above the highest ever used" is written in those terms. What ends is fixed-arity
  ordinals "indexing the `cards` list from 0": they are registry slots that merely happen to start low.
- **ADR-0002 §6** — the ordinal is *the slot declared by the kind definition* (cloze: `0x8000 | n`),
  not the index into the `cards` list. The `CardRef` shape and its 18-byte canonical encoding are
  unchanged.
- **ADR-0002 §7** — its amendment note from ADR-0012 §6 is discharged. Absorbing a kind change no
  longer reattaches history to a semantically different card; the "same mechanism absorbs a note
  changing kind" claim is restored to true as written.
- **ADR-0012 §2** — the dropdown lists the shipped kinds plus the note's own current kind when that
  kind was acquired (§6 above).
- **ADR-0012 §5** — its ambient dormancy warning now absorbs the kind change, which needs nothing added
  to it. Its "in ordinal position" rule is flagged in §5 above for the visual design pass.
- **ADR-0012 §6** — closed. Its bespoke kind-change warning is retired, and its open item *"`CardRef`
  and the kind discriminator — ADR-0002's decision to take"* is discharged by this ADR.

## Consequences

- **No persisted artifact changes.** The log, the fuzz seed, the `.ldeck` format and ADR-0010's
  suspension keys are byte-identical to what they would have been. The whole decision lives in how a
  kind definition is written and how cards are generated from it — `leitner-core`, with no dependency
  added (ADR-0009 §1).
- **Adding a kind stops being purely local.** It means taking the next free slot from a registry that
  may never reuse a number, rather than writing a self-contained definition. This is the same class of
  rule as ADR-0002 §2's "a kind identifier is never reused", and it replaces one that was strictly more
  dangerous and could not be tested.
- **Two tests are now owed** and they are among the highest-value in the repository, alongside
  ADR-0009's merge-commutativity property test: slot uniqueness across shipped definitions, and slot
  immutability against a golden `slot → (prompt, answer)` list. Both need no database, no window and no
  handset.
- **Raw log rows are less readable for cloze.** `ordinal 32769` means blank 1. A diagnostic tool should
  decode it; a person reading a line by hand must know the rule.
- **A future kind wanting to inherit an existing kind's history has a supported way to do it** —
  sharing a slot — where previously it had none, and the only lever was a positional coincidence.
